Paper · arXiv:2310.08560

1. Introduction

LLM은 응답을 생성할 때 현재 입력에 포함된 정보를 참조함.

대화나 문서가 길어지면 context window에 모든 내용을 넣을 수 없으므로, 이전 내용을 제거하거나 요약해야 함.

Context window를 늘리는 방법도 있지만, 입력이 길어질수록 연산과 메모리 비용이 증가함. 또한 긴 입력의 중간에 있는 정보를 충분히 활용하지 못하는 문제도 있음.

운영체제는 물리 메모리보다 큰 데이터를 다루기 위해, 메모리와 디스크 사이에서 필요한 데이터를 이동시킴.

MemGPT는 이를 LLM의 입력 관리에 적용한 Virtual Context Management를 제안함.

  • 현재 추론에 필요한 정보는 main context에 배치
  • 전체 대화 기록과 문서는 external context에 보관
  • LLM이 함수 호출로 정보를 저장·검색하고, 현재 입력에 포함할 내용을 관리

이를 통해 정해진 context window 안에서 필요한 정보를 교체하면서 긴 대화와 문서를 처리함.

2. Design

2.1 Main Context

Main context는 현재 LLM 호출에 전달되는 입력 토큰 전체를 의미함. 다음 세 영역으로 구성됨.

구성 요소저장하는 내용관리 방식
System Instructions메모리 구조, 함수 사용법, 실행 규칙고정된 읽기 전용 지시문
Working Context사용자 정보, 선호, 에이전트의 persona 등 중요한 사실LLM이 함수 호출로 수정
FIFO Queue최근 대화, 시스템 알림, 함수 호출과 실행 결과Queue manager가 관리

Working context는 대화가 이어지는 동안 계속 참조해야 하는 정보를 보관함. 예를 들어 사용자의 이름이나 생일을 이 영역에 기록하면, 해당 내용을 처음 언급한 메시지가 FIFO queue에서 빠진 뒤에도 입력에 유지할 수 있음.

FIFO queue는 최근 메시지를 시간순으로 유지함. 맨 앞에는 queue에서 제거된 과거 메시지의 recursive summary가 들어감.

2.2 External Context

External context는 현재 LLM 입력 바깥에 보관된 정보이며, 두 저장소로 나뉨.

저장소역할예시
Recall Storage대화와 실행 이력의 원문 보관사용자 메시지, LLM 출력, 과거 대화
Archival Storage장기 보관할 정보와 외부 문서 저장업로드한 문서, 별도로 기록한 지식

Recall storage에는 새로 들어온 메시지와 생성된 LLM 출력이 기록됨. 이후 해당 메시지가 context window에서 제거되어도 원문을 검색할 수 있음.

Archival storage에는 LLM이 함수 호출로 정보를 저장하거나, 분석 대상 문서를 미리 넣을 수 있음. 외부 저장소의 내용을 응답에 활용하려면 검색 결과를 main context로 가져와야 함.

2.3 Memory Management and Control Flow

새 메시지가 들어왔을 때

  1. Queue manager가 새 메시지를 FIFO queue에 추가
  2. System instructions, working context, FIFO queue를 연결하여 LLM 입력을 구성
  3. LLM이 응답 또는 함수 호출을 생성
  4. 들어온 메시지와 생성된 출력을 recall storage에 기록
  5. 함수 호출이 있으면 실행하고, 그 결과를 다시 main context에 추가

과거 기록을 검색한 경우에도 검색 결과가 queue에 추가되므로, 다음 LLM 호출에서 해당 내용을 확인할 수 있음.

Context window capacity alert

Queue manager는 입력 토큰 수를 확인하여 공간 부족에 대응함.

① Memory pressure warning

입력이 경고 임계값에 도달하면 시스템 메시지로 공간 부족을 알림. 논문에서는 context window의 70%를 예로 제시함.

LLM은 이 알림을 보고 최근 대화의 중요한 사실을 working context나 archival storage에 기록할 수 있음.

② Queue flush와 recursive summarization

입력이 flush 임계값에 도달하면 오래된 메시지를 일정량 제거함. 논문은 임계값 100%, 제거량 context window의 50%에 해당하는 메시지를 예로 듦.

이때 기존 요약과 새로 제거되는 메시지를 함께 요약하여 recursive summary를 갱신함.

따라서 context window에는 최근 대화와 과거 요약이 남고, 제거된 메시지의 원문은 recall storage에서 검색할 수 있음.

Retrieval

현재 입력에 필요한 정보가 없으면 LLM이 recall storage 검색 함수를 호출함.

예를 들어 사용자가 “놀이공원에 다녀왔다”고 말하면, MemGPT는 과거 대화에서 해당 장소를 검색하여 누구와 관련된 곳인지 확인할 수 있음.

검색 결과는 pagination으로 나누어 반환함. LLM은 먼저 받은 결과를 확인한 뒤, 부족하면 다음 페이지를 요청함. 한 번의 검색으로 너무 많은 정보가 입력에 들어가는 것을 조절하는 방식임.

Message update

Working context의 정보는 새로운 대화에 맞춰 수정할 수 있음.

Function Executor와 Heartbeat

LLM은 어떤 정보를 검색하거나 수정할지 결정하고, function executor가 실제 함수를 실행함.

Executor는 함수 이름과 인자를 확인한 뒤 실행 결과를 반환함. 오류가 발생하면 오류 내용도 LLM 입력에 전달하여, 다음 호출에서 행동을 수정할 수 있도록 함.

여러 번의 함수 실행이 필요한 작업에서는 request_heartbeat=true를 사용함.

  • Heartbeat를 요청하면 함수 실행 후 결과를 추가하고 LLM을 다시 호출함.
  • LLM은 결과를 읽고 추가 검색이나 메모리 수정을 이어갈 수 있음.
  • 실행 제어를 넘기면 다음 사용자 메시지나 외부 이벤트가 들어올 때까지 기다림.

예를 들어 검색 → 결과 확인 → 다음 페이지 검색 → 답변을 하나의 사용자 요청 안에서 이어서 수행할 수 있음.

사용자 메시지 외에도 메모리 경고, 문서 업로드 완료 알림, 예약된 이벤트 등이 LLM 실행을 시작하는 계기가 될 수 있음.

3.2 Deep Memory Retrieval — 과거 대화의 사실 찾기

Multi-Session Chat 데이터셋의 과거 5개 세션을 바탕으로, 이전 대화를 알아야 답할 수 있는 질문을 추가함.

  • Baseline은 이전 대화의 손실 요약을 입력으로 받음.
  • MemGPT는 전체 대화 원문에 접근할 수 있지만, 필요한 내용을 recall storage에서 검색해야 함.

정확도는 LLM judge로 평가하고, 정답 표현이 얼마나 포함되었는지 ROUGE-L recall도 측정함.

3.3 Conversation Opener — 사용자 정보를 활용한 대화 시작

과거 대화에서 알게 된 사용자 정보로 새로운 대화를 시작하도록 함.

예를 들어 사용자가 이전에 여행 계획을 이야기했다면, 다음 대화에서 여행이 어땠는지 먼저 물어볼 수 있음. Working context에 유지한 사용자 정보를 질문 없이도 응답에 활용하는 과제임.

생성한 문장과 사용자 persona 정보 사이의 유사도인 SIM-1·SIM-3, 사람이 작성한 시작 문장과의 유사도인 SIM-H를 측정함.

3.4 Multi-document QA — 여러 문서에서 답 찾기

NaturalQuestions-Open에서 선택한 50개 질문과 Wikipedia 문서를 사용함.

Baseline은 검색한 상위 K개 문서를 입력에 넣고 답변함. 문서가 context window에 들어가지 않으면 각 문서를 잘라서 넣음.

MemGPT는 문서를 archival storage에 보관하고, 필요한 내용을 함수 호출로 검색함. 한 번의 검색에서 충분한 근거를 찾지 못하면 추가 검색이나 다음 페이지 조회를 수행할 수 있음.

문서 검색에는 임베딩 기반 유사도 검색을 사용하며, 실험 구현은 PostgreSQL, pgvector, HNSW index를 활용함.

논문은 MemGPT도 정답 문서를 찾기 전에 검색을 중단하는 경우가 있다고 보고함. 원문이 저장되어 있어도, 실제 답변에 활용하려면 LLM이 충분한 검색을 수행해야 함.

3.5 Nested Key-value Retrieval — 다단계 검색

일반적인 key-value 조회는 주어진 key의 value를 찾으면 끝남. Nested KV에서는 찾은 value가 다시 다른 항목의 key일 수 있으므로, 최종 값에 도달할 때까지 조회를 이어가야 함.

예를 들어 A → B, B → C가 저장되어 있다면, A를 조회해 얻은 B를 다음 검색에 사용하고 최종적으로 C를 반환해야 함.

실험은 140개의 key-value 쌍, 약 8K tokens로 구성하고, 중첩 수준과 항목의 배치를 바꾸어 수행함.

4. Conclusion

MemGPT는 main context, 외부 저장소, 함수 호출, 이벤트 기반 실행을 결합하여 장기 기억을 관리함.

최근 대화는 FIFO queue에 유지하고, 중요한 사실은 working context에 기록함. 과거 대화와 문서의 원문은 외부 저장소에 보관하며, 필요한 시점에 검색하여 현재 입력으로 가져옴. 공간이 부족해지면 오래된 메시지를 제거하고 recursive summary를 갱신함.

실험에서는 과거 대화의 세부 정보 검색과 다단계 문서 조회에서 성능이 개선됨. 검색을 얼마나 이어갈지와 어떤 정보를 저장할지를 LLM이 결정하므로, 기반 모델의 함수 호출 및 실행 제어 능력이 결과에 영향을 줌.
