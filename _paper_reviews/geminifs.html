Question & Answer of my own

File System

File은 저장 단위이며, 일반적으로 Record 또는 Block 단위로 비휘발성 보조기억장치(ex. SSD)에 저장됨

컴퓨터 시스템의 편리한 사용을 위해 OS는 다양한 저장 장치를 file이라는 동일한 논리적 단위로 볼 수 있게 해줌

ex) create, read, write, reposition(lseek), delete, open, close 등의 연산

File attribute(metadata)는 파일 자체의 내용이 아니라 파일을 관리하기 위한 각종 정보

ex) 파일 이름, 유형, 저장된 위치, 파일 사이즈, 접근 권한(읽기/쓰기/실행), 소유자, 시간(생성/변경/사용) 등 파일에 대한 전반적인 정보

File System은 OS와 모든 데이터, 프로그램의 저장과 접근을 위한 기법을 제공, 시스템 내의 모든 파일에 관한 정보를 제공해주는 디렉터리 구조이고, 파일 및 파일의 metadata, 디렉터리 정보 등을 관리

GPUfs, Dragon

1. GPUfs

먼저, 어떤 불편이 있었을까요?

숫자가 들어 있는 data.bin 파일을 GPU로 계산한다고 해보겠습니다.

기존에는 개발자가 대체로 다음 작업을 나누어 작성해야 했습니다.

  • CPU에서 실행할 코드: 파일을 열고, 숫자를 읽고, GPU 메모리로 보내기
  • GPU에서 실행할 코드: 전달받은 숫자로 계산하기

GPU 계산 코드는 CPU가 미리 준비해 준 데이터를 받아 계산하는 형태인 것입니다.

그런데 계산 중에 **“다음에는 파일의 다른 부분이 필요하네?”**라는 상황이 생기면 어떻게 될까요?

개발자는 GPU의 계산과 CPU의 데이터 준비가 맞물려 움직이도록 코드를 작성해야 합니다. 어떤 데이터를 언제 가져올지까지 신경 써야 하므로 프로그램이 복잡해집니다.

GPUfs는 무엇을 제공하나요?

GPUfs는 GPU에서 실행하는 코드 안에서도 파일 읽기 함수를 사용할 수 있게 합니다.

개발자는 GPU 계산 코드에 다음과 같은 요구를 표현할 수 있습니다.

“계산하려면 data.bin의 이 부분이 필요하니 읽어 주세요.”

여기서 중요한 것은 개발자가 파일 접근을 요청할 수 있는 위치가 GPU 코드 안으로 확장됐다는 점입니다.

그렇다면 GPU가 혼자 SSD에서 가져오나요?

필요한 데이터가 아직 메모리에 없는 경우, 내부에서는 다음처럼 동작합니다.

  1. GPU 코드가 파일 읽기를 요청합니다.
  2. GPUfs가 그 요청을 CPU에서 실행되는 도우미 코드에 전달합니다.
  3. 도우미 코드가 기존 운영체제의 파일 읽기 기능을 사용합니다.
  4. SSD의 데이터를 CPU 메모리로 가져옵니다.
  5. 데이터를 GPU 메모리로 전송합니다.
  6. GPU 코드가 그 데이터를 사용해 계산합니다.

즉, CPU가 하던 일을 개발자가 직접 작성하는 부담을 GPUfs가 대신 처리합니다. 내부적으로는 CPU의 도움이 계속 필요합니다.

GPUfs는 가져온 데이터를 GPU 메모리에 보관해 두기도 합니다. 이것을 캐시라고 합니다. 같은 데이터를 다시 요청하면 보관해 둔 것을 사용하여, CPU와 SSD에 다시 요청하는 일을 줄일 수 있습니다.

2. Dragon

어떤 불편을 해결하려 했을까요?

이번에는 숫자 배열이 저장된 파일이 100GB인데, GPU 메모리는 16GB뿐인 상황을 가정하겠습니다. 설명을 위한 예시입니다.

100GB를 GPU 메모리에 한꺼번에 넣을 수 없으므로, 개발자는 보통 다음 과정을 관리해야 합니다.

  1. 파일의 일부만 읽습니다.
  2. GPU 메모리로 보냅니다.
  3. 해당 부분을 계산합니다.
  4. 다음 부분으로 교체하고 계산을 반복합니다.

문제는 계산이 항상 앞에서 뒤로 진행되지는 않는다는 것입니다. 계산 중 어느 위치의 숫자가 필요할지 달라진다면, 데이터를 나누어 가져오는 코드도 복잡해집니다.

Dragon은 어떻게 사용하게 하나요?

Dragon은 파일에 들어 있는 숫자를 메모리 배열처럼 접근할 수 있도록 연결합니다.

개발자가 처음에 파일과 메모리 주소를 연결해 두면, GPU 계산 코드에서는 다음처럼 사용할 수 있습니다.

“이 배열의 첫 번째 숫자를 사용하겠습니다.”

프로그래밍 표현으로는 p[0] 같은 접근입니다.

이때 100GB 전체를 GPU 메모리에 넣어 둔 것은 아닙니다. 파일의 각 부분에 메모리 주소를 대응시켜 두고, 실제로 필요한 부분을 나중에 가져올 수 있게 한 것입니다. 이렇게 연결하는 것을 **매핑(mapping)**이라고 합니다.

필요한 숫자가 GPU 메모리에 없다면 어떻게 되나요?

  1. GPU가 배열의 특정 위치에 접근합니다.
  2. 시스템이 **“그 데이터가 아직 GPU 메모리에 없네?”**라는 상황을 감지합니다.
  3. 해당 접근을 잠시 기다리게 합니다.
  4. CPU에서 실행되는 Dragon 처리 코드가 파일의 어느 부분이 필요한지 찾습니다.
  5. 필요한 데이터를 CPU 메모리로 가져오고, GPU 메모리로 옮깁니다.
  6. GPU가 기다리던 접근을 이어서 수행합니다.

메모리에 없는 데이터에 접근하여 시스템의 처리가 필요해진 상황을 여기서는 **페이지 폴트(page fault)**라고 부릅니다.

GPU 메모리가 가득 차면 기존 데이터 일부를 내보내어 새 데이터가 들어갈 공간을 만듭니다. 이 과정을 반복하므로 GPU 메모리보다 큰 파일도 필요한 부분을 교체하면서 처리할 수 있습니다.

BaM

BaM은 “GPU가 필요한 데이터를 CPU에게 가져다 달라고 부탁하지 않고, SSD에 블록처리 직접 요청하자”

GPUfs와 비교하면서 설명드리겠습니다.

1. 어떤 불편을 해결하려 했나요?

GPUfs에서는 GPU가 파일 읽기를 요청해도, 실제로 파일을 읽고 데이터를 전달하는 일은 CPU 측 코드가 처리했습니다.

GPU에서 계산하는 수많은 스레드가 동시에 서로 다른 데이터를 요구하면, CPU에 요청이 몰리고 CPU–GPU 사이의 통신도 많아집니다.

BaM은 계산 중 필요한 데이터가 결정되는 작업에서, GPU가 직접 스토리지 접근을 처리하도록 합니다.

2. GPU가 SSD에 어떻게 직접 요청하나요?

먼저 큐(queue)는 처리할 요청을 적어 두는 공간이라고 생각하시면 됩니다.

예를 들어 다음과 같은 요청입니다.

“SSD의 이 위치에서 데이터를 읽어서, GPU 메모리의 저 위치에 넣어 주세요.”

BaM은 이러한 요청을 적는 공간과 완료 정보를 받는 공간을 GPU 메모리에 만듭니다. 이를 NVMe 요청 큐와 완료 큐라고 합니다.

필요한 데이터가 아직 GPU 메모리에 없다면 다음처럼 동작합니다.

  1. GPU 코드가 필요한 데이터를 찾습니다.
  2. BaM이 SSD에 보낼 읽기 명령을 만듭니다.
  3. GPU가 요청 큐에 명령을 넣고 SSD에 알립니다.
  4. SSD 컨트롤러가 요청을 확인하고 데이터를 읽습니다.
  5. SSD가 데이터를 GPU 메모리로 직접 전송합니다.
  6. SSD가 완료 정보를 남기면 GPU가 확인하고 계산을 계속합니다.

중간에서 CPU에게 요청을 전달하여 대신 처리하게 하는 단계가 빠짐

3. 매번 SSD까지 읽으러 가나요?

BaM도 GPU 메모리에 가져온 데이터를 보관하는 캐시를 둡니다.

  • 필요한 데이터가 이미 있으면 GPU 메모리에서 바로 사용합니다.
  • 없을 때만 SSD에 요청합니다.
  • 여러 스레드가 같은 데이터를 요구하면 중복된 SSD 요청을 줄입니다.

또한 많은 GPU 스레드가 요청 큐를 효율적으로 사용할 수 있도록 설계했습니다. 단순히 CPU의 일을 GPU로 옮기는 것에 더해, GPU의 많은 동시 요청을 처리하는 구조를 만든 것입니다.

4. 그러면 CPU는 아예 필요 없나요?

초기 설정과 GPU 계산 실행 등에는 CPU가 사용됩니다. BaM이 제거하려는 것은 계산 중 발생하는 각각의 스토리지 요청을 CPU가 대신 처리하는 의존성입니다.

5. 그런데 GeminiFS는 BaM의 무엇을 문제 삼나요?

SSD의 특정 블록을 읽는 기능과, 파일을 관리하는 기능은 다르기 때문입니다.

설명을 위한 예로 비교하면 다음과 같습니다.

접근 수준프로그램의 요구
파일 단위“data.bin의 앞부분을 읽어 주세요.”
블록 단위“SSD의 100번 블록부터 읽어 주세요.”

파일 단위로 사용하려면 파일 이름, 크기, 저장 위치, 접근 권한 등을 관리하는 파일 시스템이 필요합니다.

GeminiFS 저자는 BaM이 SSD 직접 접근은 제공하지만, 기존 호스트 파일 시스템의 파일 관리 기능을 그대로 제공하지는 못한다고 지적합니다. >> BaM은 GPU에서 사용할 수 있는 파일 시스템을 제공하지 않음

PCIe

(Bus의 일종) 주변 장치(GPU, NIC, SSD)를 CPU 및 메모리와 연결하는 데 사용되는 표준 인터페이스

여러 장치가 1개의 도로를 나눠써서 신호가 꼬이거나 속도가 느렸던 이전과 달리 CPU와 장치가 직접 연결되는 lane이 있고 스위치가 교통정리를 해줘서 병목이 없음. 차선 수는 적지만 속도가 매우 빠르다.

NVMe

위에 PCle를 사용하는 전체적인 구조를 의미함

SPDK(Storage Performance Development Kit)

CPU의 성능을 극대화하고 NVMe 장치와 같은 최신 스토리지 하드웨어에 대한 I/O 작업을 빠르고 효율적으로 수행할 수 있도록 하는 오픈소스 소프트웨어 프레임워크

1. Introduction

GPU에서 스토리지 접근이 중요한 이유

  • GNN, LLM과 같은 ML 애플리케이션은 대규모 학습 데이터, 모델 가중치, activation, KV cache 등을 사용함. 이러한 데이터는 GPU 메모리인 HBM의 용량을 초과할 수 있으므로, 일부 데이터를 외부에 저장하고 필요할 때 가져와야 함.
  • GPU 메모리를 확장하는 방법으로 CPU 메모리나 다른 GPU의 메모리를 활용할 수 있지만 비용이 큼. 따라서 상대적으로 저렴하고 용량이 큰 NVMe SSD를 GPU 메모리의 확장 공간으로 활용하는 방법이 연구되고 있음.

기존 접근 방식의 한계

  • CPU-centric 방식은 CPU가 스토리지 접근을 제어함. GPU가 데이터를 필요로 할 때 CPU가 요청을 처리하고 데이터 전송을 준비하므로, CPU–GPU 간 통신과 동기화가 발생함. 수많은 GPU 스레드가 동시에 요청하면 CPU의 처리 능력이 병목이 될 수 있음.
  • GPU-centric 방식은 GPU가 직접 NVMe 요청을 제출함. 대표적인 BaM은 CPU의 개입 없이 SSD에 접근하여 높은 병렬성을 활용하지만, 파일 시스템이 제공하는 파일 추상화와 관리 기능이 부족함. 애플리케이션이 raw block device를 다뤄야 하므로, 기존 호스트 파일의 접근이나 프로세스 간 데이터 공유가 복잡해짐.

GeminiFS의 핵심 아이디어

  • GeminiFS는 기존 호스트 파일 시스템과 함께 동작하는 Companion File System을 제안함.
    • 호스트: 파일 생성, 공간 할당, 디렉터리 관리 등 복잡한 파일 관리 담당
    • GPU: 호스트가 준비한 메타데이터를 이용하여 파일 데이터를 직접 읽고 씀
  • 파일 관리에는 기존 파일 시스템을 활용하면서, 실제 데이터 접근 경로에서는 GPU가 CPU를 거치지 않고 SSD에 요청을 보낼 수 있도록 하는 것이 목표임.

2. Background and Motivation

2.1 ML 워크로드의 스토리지 접근 특성

ML 애플리케이션의 데이터는 수명과 접근 방식에 따라 구분할 수 있음.

구분예시주요 특성
단기 데이터 (Short term)학습 중 생성되는 중간 activation, 중간 계산 결과짧은 시간만 필요하며, 일반적으로 영속성 보장이 불필요함
장기 데이터 (Long term)학습 입력, 모델 가중치, 재사용하는 KV cache생성 과정에서 순차적으로 기록하거나 append한 뒤, 주로 읽기 위주로 접근함

또한 모델 구조와 설정을 통해 필요한 데이터 크기와 접근 패턴을 어느 정도 예측할 수 있으며, 여러 GPU 프로세스가 동일한 모델 가중치나 KV cache를 공유하기도 함.

GeminiFS는 이러한 특성을 이용함. 필요한 파일 공간을 미리 할당하고, GPU가 접근하는 동안 파일의 블록 배치를 안정적으로 유지하면, 복잡한 메타데이터 변경을 매번 CPU와 조율할 필요가 줄어듦.

2.2 CPU-centric vs. GPU-centric Storage Access

스토리지 접근은 Control plane과 Data plane으로 나누어 볼 수 있음.

  • Control plane: I/O 명령을 만들고 제출하며 완료를 확인하는 경로
  • Data plane: SSD와 GPU 메모리 사이에서 실제 데이터가 이동하는 경로

GPUfs, Dragon과 같은 CPU-centric 시스템에서는 GPU의 요청을 CPU가 처리함. GDS는 SSD와 GPU 사이의 직접 데이터 전송을 지원하지만, 전송을 시작하고 제어하는 역할은 CPU가 담당함.

BaM은 NVMe I/O queue를 GPU 메모리에 배치하여 GPU 스레드가 직접 명령을 제출하도록 함. 따라서 데이터 전송뿐 아니라 I/O 제어 경로에서도 CPU 의존성을 줄일 수 있음.

CPU-centric 방식에서는 SSD가 빨라져도 소프트웨어 처리 비용이 전체 지연시간에서 큰 비중을 차지함. 특히 GPU의 높은 병렬성을 CPU가 충분히 처리하지 못하면 요청이 몰리면서 평균 지연시간과 tail latency가 증가함.

2.3 GPU 파일 시스템의 설계 과제

GPU가 직접 SSD에 접근하면서 파일 인터페이스를 제공하려면 다음 문제가 해결되어야 함.

  1. 메타데이터 공유: 호스트가 관리하는 파일의 위치와 속성을 GPU에서도 알아야 함.
  2. NVMe 드라이버 지원: 하나의 SSD에 CPU와 GPU의 I/O queue를 함께 구성해야 함.
  3. GPU page cache: 수많은 스레드의 캐시 접근에서 lock contention을 줄여야 함.
  4. 프로그래밍 복잡도: 애플리케이션이 메타데이터, 메모리 매핑, NVMe queue를 직접 관리하는 부담을 줄여야 함.

3. GeminiFS

3.1 전체 구조

GeminiFS는 다음 네 요소로 구성됨.

구성 요소역할
GVDKGPU의 파일 접근에 필요한 메타데이터와 블록 매핑을 파일 내부에 저장

3.2 Metadata Embedding: GVDK

파일을 읽으려면 파일 내부의 논리적 위치가 SSD의 어느 블록에 해당하는지 알아야 함.

예를 들어 GPU가 “이 파일의 특정 offset부터 읽기”를 요청하면, 해당 offset을 NVMe 장치에서 접근할 블록 위치로 변환해야 함. 일반적인 파일 시스템은 이를 위해 복잡한 인덱스 구조를 사용하지만, 이러한 구조를 GPU에서 그대로 처리하면 분기와 제어 비용이 커짐.

GeminiFS는 호스트에서 파일 공간을 미리 할당한 뒤, 필요한 메타데이터를 파일 내부에 저장하는 GVDK(GPU Virtual Disk) 형식을 사용함.

주요 메타데이터는 다음과 같음.

(GPU가 이 파일을 읽고 쓰는 데 필요한 파일별 정보)

  • 파일 크기와 접근 모드
  • I/O block 크기
  • 파일 offset과 NVMe offset의 매핑 (파일 내 위치를 SSD의 NVMe 블록 위치로 변환)
  • 페이지 기록 상태를 관리하는 bitmap (여러 GPU thread가 같이 공유하니깐 어떤 데이터 블록에 쓰기가 발생했는지 추적)

호스트의 GVDK helper가 파일의 블록 위치를 구하여 매핑을 만들고, 파일을 열 때 GPU 메모리로 가져옴. GPU는 이후 해당 매핑을 이용하여 주소를 직접 변환함. 블록 매핑 저장에 필요한 공간 오버헤드는 약 **0.2%**임.

주소 변환에는 2단계 매핑 테이블을 사용함.

  1. L1 index: 접근할 L2 table의 위치를 찾음.
  2. L2 index: 실제 데이터 블록의 NVMe offset을 찾음.
  3. Block offset: 해당 블록 내부의 바이트 위치를 찾음.

디렉터리 관리나 새로운 블록 할당은 호스트가 담당하므로, GPU는 데이터 접근에 필요한 비교적 단순한 메타데이터만 처리하면 됨.

3.3 CPU/GPU Shared NVMe Driver: SNVMe

NVMe는 **Submission Queue(SQ)**에 명령을 제출하고, **Completion Queue(CQ)**에서 완료 여부를 확인하는 방식으로 동작함.

GeminiFS는 기존 호스트 NVMe 드라이버를 확장하여 CPU 메모리와 GPU 메모리에 각각 I/O queue를 구성함.

  • CPU는 NVMe controller 초기화와 관리 작업을 담당함.
  • GPU 메모리의 queue를 SSD가 접근할 수 있도록 DMA 주소로 매핑함.
  • GPU 스레드는 SQ에 직접 I/O 명령을 제출하고, CQ를 polling하여 완료를 확인함.

이 구조에서는 CPU와 GPU가 동일한 NVMe 장치를 사용하면서도 각자의 queue를 통해 요청을 제출할 수 있음. 초기 설정은 호스트에서 수행하고, GPU의 개별 데이터 접근은 CPU의 요청 처리 없이 진행됨.

3.4 GPU-Specific Page Cache

Page cache는 SSD에서 읽은 데이터를 GPU 메모리에 보관하여 재사용함. 캐시에 데이터가 있으면 SSD 접근 대신 GPU 내부 메모리 대역폭을 활용할 수 있음.

GPU에서는 많은 스레드가 동시에 캐시에 접근하므로 lock contention이 주요 문제가 됨. GeminiFS는 다음 방법을 사용함.

  • Warp 단위 페이지 획득: 개별 스레드가 각각 캐시를 관리할 때보다 경합을 줄임.
  • 상수 시간 자료구조: Hash table과 doubly linked list를 이용하여 조회 및 교체 관리의 임계 구역을 짧게 유지함.
  • 프로세스 간 캐시 공유: 동일한 파일의 캐시를 inter-process memory handle로 공유하여 중복 메모리 사용을 줄임.
  • 설정 조절: Page 크기, 캐시 용량, prefetch 수를 워크로드에 맞게 조절함.

순차 접근에서는 한 번의 cache miss에 여러 페이지를 미리 가져오는 prefetching으로 충분한 I/O 병렬성을 확보할 수 있음.

3.5 Programming Model: libGemini

libGemini는 내부 구현을 감추고 파일 접근 API를 제공함.

실행 위치주요 API역할
HostGeminifs_init, G_open시스템 초기화, 파일 준비, 메타데이터·캐시 설정
GPUG_read, G_write파일의 지정된 offset에서 데이터 읽기·쓰기
GPUG_sync변경된 데이터와 메타데이터를 저장장치에 반영

G_read와 G_write는 접근 권한과 파일 범위를 확인하고, offset을 NVMe 주소로 변환한 뒤 I/O를 수행함.

전체 POSIX 기능을 구현하지는 않으며, 영속성이 필요한 데이터는 애플리케이션이 G_sync를 호출하여 저장을 요청하도록 함. 이는 임시 데이터가 많은 ML 워크로드의 특성을 반영한 설계임.

4. Evaluation

4.1 기존 시스템과의 I/O 성능 비교

실험은 64-core CPU, 512 GB 호스트 메모리, 80 GB HBM GPU, Intel Optane P5800X SSD 환경에서 수행함. 호스트 파일 시스템으로 EXT4를 사용함.

GPUfs, GDS, BaM과 4 KB 읽기 성능을 비교하며, GeminiFS의 캐시를 우회하여 직접 I/O 경로의 성능을 측정함.

Bandwidth

GPUfs와 GDS는 요청이 증가하면 CPU 처리와 스레드 경합의 영향을 받음. GeminiFS는 GPU가 직접 요청을 제출하여 병렬성을 높이고, 1,024 threads에서 SSD의 최대 대역폭에 도달함.

BaM과 비교하면 메타데이터 확인과 주소 변환이 추가되지만, 대역폭 감소는 약 **4.6%**로 작음.

Latency

GeminiFS는 CPU의 소프트웨어 처리와 CPU–GPU 간 요청 전달 비용을 줄여 높은 병렬성에서 지연시간 증가를 완화함.

BaM 대비 지연시간 증가는 약 **4.8%**로, 파일 인터페이스를 제공하면서도 raw-device 접근과 유사한 성능을 유지함.

4.2 Page Cache 성능

Page cache 실험에서는 SSD 대역폭이 결과를 제한하지 않도록 NVMe 접근을 메모리 복사로 대체함. 따라서 아래 결과는 GPU page-cache 경로의 처리 성능을 나타냄.

Prefetching

Prefetch를 사용하지 않으면 충분한 데이터를 동시에 처리하기 어려움. Prefetch를 활성화하면 후속 페이지를 함께 가져와 순차 읽기·쓰기 대역폭이 크게 향상됨.

Warp 수

Warp 수를 늘리면 더 많은 메모리 요청을 동시에 처리할 수 있음. GeminiFS의 캐시는 높은 병렬성에서도 처리량이 증가하여, GPU의 병렬성을 활용할 수 있음을 보여줌.

Page 크기

같은 범위의 데이터를 접근하더라도 page가 크면 관리해야 하는 page 수가 줄어듦. 따라서 캐시 조회와 lock 획득 빈도를 낮출 수 있음.

4.3 LLM Training 성능

GPT2-124M 학습에서 다음 두 상황을 비교함.

  • Activation을 GPU 메모리에 유지: 주로 checkpoint 저장 성능의 영향을 확인함.
  • Activation을 SSD로 offload: 대규모 중간 데이터의 읽기·쓰기 성능을 확인함.

비교 대상은 native 방식인 memcopy + read/write, GDS, DLRover-RM이며, GeminiFS의 page cache는 2 GB로 설정함.

Activation을 GPU 메모리에 유지할 때는 전체 실행시간에서 계산이 차지하는 비중이 큼. 따라서 checkpoint 쓰기를 크게 가속해도 전체 학습시간의 개선 폭은 상대적으로 작음.

Activation을 offload하면 많은 소규모 I/O가 발생하여 CPU–GPU 간 빈번한 요청 조율이 부담이 됨. GeminiFS는 직접 I/O와 GPU page cache를 이용하여 이 비용을 줄임.

실제 애플리케이션 평가는 GPT2-124M의 3개 학습 step을 대상으로 수행함. 포괄적인 multi-GPU 지원과 다중 SSD 활용은 향후 과제로 제시함.
