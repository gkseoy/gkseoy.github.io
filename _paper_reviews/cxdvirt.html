    • 실제 장치가 없어도, 프로그램이 그 장치가 연결된 것처럼 사용할 수 있게 동작을 흉내 내는 도구
  • NAND 플래시
    • SSD 안에서 데이터를 저장하는 칩
    • 전원을 꺼도 데이터가 남고, DRAM보다 용량을 크게 만들기 쉽지만 읽는 속도는 느림
    • 이 논문의 CXL-SSD는 그래서 작고 빠른 DRAM 캐시에 데이터의 복사본을 두고, 캐시에 없으면 크고 느린 NAND에서 가져오는 구조
  • FEMU
    • Cylon 안에서 SSD 내부 동작을 맡는 에뮬레이터
    • Cylon은 가상 NAND에 해당하는 데이터를 실제로는 호스트 DRAM에 저장
    • DRAM에서 그대로 읽으면 너무 빨리 끝나므로, FEMU가 실제 NAND였다면 읽는 데 얼마나 걸릴지 계산해 그 지연을 재현
  • VM
    • QEMU
      • 호스트에서 실행되는 프로그램
      • VM 안의 운영체제에 가상 디스크나 네트워크 카드 같은 장치를 제공하고, 그 장치에 대한 요청을 처리. Cylon에서는 가상의 CXL-SSD를 보여주는 역할을 함
    • KVM
      • 호스트 Linux 커널의 가상화 기능
      • CPU의 하드웨어 가상화 기능을 이용해 VM 안의 명령을 호스트의 실제 CPU에서 직접 실행할 수 있게 함. Cylon에서 가상 장치의 처리가 필요한 접근이 발생하면, VM 실행을 잠시 멈추고 요청을 QEMU에 넘김
    • Cylon에서는 하나의 가상 머신을 실행하는 데 QEMU와 KVM이 함께 쓰임.
      • 쉽게 말하면 QEMU는 VM 안에 어떤 장치가 보일지 만들고, KVM은 VM 안의 코드가 실제 CPU에서 실행되도록 도움

      ex) Cylon에서 가상 CXL-SSD의 DRAM 캐시 미스가 나면
      → VM의 실행이 잠시 멈추고(VM exit)
      → KVM이 요청을 받아 QEMU의 가상 CXL 장치로 전달
      → FEMU가 NAND 접근 지연을 재현
      → 캐시 히트라면 이 경로를 거치지 않고 캐시에서 바로 읽음

  • VM Exit
    • VM Exit이 발생하는 상황
      • 게스트 OS가 하드웨어 자원을 직접 건드리려고 하는 특수한 상황에서만 발생
      • 특권 명령어(Privileged Instructions): CPU의 핵심 제어 레지스터(CR0, CR3 등)를 변경하거나 CPU 모드를 바꾸는 명령어를 실행할 때 발생합니다.
      • 외부 하드웨어 I/O 접근: 가상 디스크에 데이터를 쓰거나 네트워크 카드로 패킷을 보내는 등 외부 장치와 통신(MMIO, Port I/O)하려 할 때 발생합니다.
      • 외부 인터럽트(External Interrupts): 호스트의 물리적 타이머가 만료되거나, 물리 네트워크 카드로 실제 패킷이 도착했을 때 호스트가 이를 처리하기 위해 게스트를 잠시 멈추고 빠져나옵니다.
      • 메모리 페이지 폴트(EPT Violation): 게스트가 할당받지 않은 물리 메모리 영역에 처음 접근하려 할 때, 호스트가 메모리를 매핑해 주기 위해 발생합니다.
      • CPUID 명령어 실행: 게스트가 현재 실행 중인 CPU의 사양이나 기능을 확인하려고 CPUID 명령어를 호출할 때, 하이퍼바이저가 가상화된 CPU 정보를 건네주기 위해 발생합니다.
    • 문제점
      • CPU 상태 저장 및 복원: 게스트의 레지스터, 플래그, 제어 상태 등을 메모리(VMCS/VMCB)에 저장하고 호스트의 상태를 불러오는 데 수백에서 수천 CPU 사이클이 소모됩니다.
      • 캐시 및 TLB 오염(Cache & TLB Pollution): 호스트 커널이나 QEMU 프로세스가 실행되면서 기존 게스트가 사용하던 CPU L1/L2 캐시와 TLB(주소 변환 버퍼) 데이터가 밀려납니다. 다시 게스트로 복귀(VM Entry)했을 때 캐시 미스(Cache Miss)가 급증하여 실행 속도가 느려집니다.
      • 파이프라인 초기화: CPU 내부의 명령어 파이프라인과 분기 예측기(Branch Predictor) 정보가 초기화되어 연산 효율이 떨어집니다.

1. Introduction

CXL-SSD란?

  • CXL-SSD
    • 작은 DRAM 캐시와 대용량 NAND를 결합하여 메모리 용량을 확장하는 장치
    • 애플리케이션은 데이터를 메모리 주소에 매핑하고, CPU의 load와 store 명령으로 접근할 수 있음
  • DRAM hit — 필요한 데이터가 장치의 DRAM 캐시에 있어 바로 접근
  • DRAM miss — NAND에서 데이터를 가져와야 하므로 NAND 읽기와 데이터 전송 시간이 추가

→ 따라서 같은 장치에서 빠른 DRAM hit와 느린 NAND miss라는 두 종류의 지연시간이 나타남

연구자가 DRAM 캐시 크기나 페이지 교체 정책을 바꾸려면 두 경로의 지연을 모두 재현할 수 있어야 하고, 실제 CXL-SSD 하드웨어에 접근하기 어렵기 때문에, 논문은 실제 애플리케이션을 실행하며 장치의 동작을 재현하는 에뮬레이터를 제안

2. Problem Definition

기존 에뮬레이터 Cylon의 지연시간

  • Cylon
    • 실제 CXL-SSD가 없어도, 가상 머신(VM)에서 CXL-SSD를 연결한 것처럼 프로그램을 실행하고 성능을 측정할 수 있게 해 주는 소프트웨어

Cylon은 QEMU/KVM 가상 머신에서 워크로드를 실행
→ DRAM miss가 발생하면 VM exit로 제어를 호스트에 넘기고, QEMU가 NAND 지연을 적용한 뒤 게스트 실행을 재개
⇒ 이 과정에서 두 종류의 비용이 발생함

  • 기본 VM 처리 비용 — KVM의 주소 변환 및 VM 진입·종료 처리, QEMU의 전역 lock 획득 및 요청 처리 등에 시간이 듭니다. 두 비용을 합하면 실험에서 miss당 3 µs 이상이었으며, 이는 실험에 사용한 고성능 NAND의 읽기 시간인 3 µs보다 큽니다.
  • 반복 VM exit와 재진입 대기 — NAND 대기가 끝나더라도 게스트가 사용할 주소 매핑이 아직 준비되지 않으면, 같은 접근을 다시 시도하면서 추가 VM exit가 발생합니다. 호스트 경합으로 게스트가 실행을 재개하기까지 기다리는 시간도 생깁니다.
    • 과도한 overhead: VM의 KVM/QEMU 스택은 메모리 접근 시 3 µs 이상의 추가 지연 시간을 발생시키는데, 이는 고성능 NAND의 응답 속도보다 길어 에뮬레이션 정확도를 떨어뜨립니다.
    • 꼬리 지연 시간(Tail Latency) 악화: VM 종료(exit) 과정에서의 다중 재시도(multi-exit refault) 및 호스트 컨텐션(contention)으로 인해 P99.9 이상의 꼬리 지연 시간이 수배에서 수십 배까지 왜곡됩니다.
    • 글로벌 락(Global Lock) 문제: QEMU의 Big QEMU Lock(BQL)으로 인해 다중 스레드 환경에서 동시성 성능이 크게 저하됩니다.

특히 tail latency에서 두 번째 문제가 크게 드러납니다. P99.9는 전체 요청의 99.9%가 완료되는 데 걸린 시간의 경계값으로, 드물게 발생하는 느린 요청을 관찰하는 데 사용합니다. 에뮬레이터 자체의 대기가 이 구간에 크게 섞이면 NAND나 캐시 정책을 바꾼 효과를 해석하기 어려워집니다.

3. Design of CXDVirt

3.1 구성 요소

CXDVirt는 VM을 완전히 제거하고 호스트 운영체제의 커널 모듈에 가상 CXL 장치를 등록하고, 애플리케이션이 호스트의 devdax 드라이버를 통해 메모리 영역을 노출하여, DRAM 히트 시 MMU(Memory Management Unit)를 통해 네이티브 속도로 데이터에 접근하여 주소 공간을 매핑하도록 함

→ 애플리케이션은 매핑된 주소를 일반 메모리처럼 읽고 쓸 수 있음

장치 내부 동작은 세 요소로 나뉩니다. Page table이 직접 접근 가능한 페이지를 나타내고, NAND 성능 모델이 읽기·쓰기·지우기 지연을 계산

Eviction과 prefetch 정책은 캐시에서 어떤 페이지를 내보낼지, 어떤 페이지를 미리 가져올지 결정하는데, 논문에서는 FIFO, LIFO, CLOCK과 다음 N개 페이지를 가져오는 next-N prefetch를 구현했음

cf) Eviction은 캐시가 찼을 때 어떤 페이지를 내보낼지 결정하는 정책

Prefetch는 현재 페이지 뒤의 N개 페이지를 미리 가져오는 정책

3.2 Page fault로 NAND 접근을 재현하는 방법

  • PTE(Page Table Entry): 가상 페이지를 물리 메모리에 연결하는 주소 매핑 정보
  • CXDVirt는 이 매핑을 설치하거나 제거하여, 다음 접근이 DRAM hit 경로와 miss 경로 중 어디로 갈지 제어함
상황 처리 과정
DRAM hit PTE가 있으면 MMU가 주소를 변환하고 실제 메모리에 바로 접근합니다.
DRAM miss PTE가 없으면 page fault가 발생합니다. CXDVirt가 NAND 읽기와 전송 지연을 계산해 기다린 뒤, PTE를 설치합니다. 이후 접근은 직접 메모리 경로를 사용합니다.
캐시에서 페이지 제거 PTE를 제거해 다음 접근에서 page fault가 발생하도록 합니다. 수정된 dirty page라면 NAND 쓰기 지연도 적용합니다.

실제 데이터는 호스트의 물리 메모리에 보관

따라서 에뮬레이터에서 말하는 DRAM과 NAND 영역은 페이지의 논리적 상태

페이지를 가져오거나 내보낼 때 주소 매핑과 상태를 바꾸므로, 두 영역 사이의 memcpy 비용을 피할 수 있음

3.3 페이지 상태와 동시 접근 관리

각 페이지는 NOT_CACHED → LOADING → CACHED → EVICTING의 상태를 가짐

1. 캐시 밖에 있는 페이지를 요청하거나 prefetch하면 LOADING으로 전환하고, NAND 읽기 지연이 끝나면 CACHED로 전환

페이지를 내보낼 때는 EVICTING 상태에서 매핑을 제거하고, dirty page라면 쓰기 지연을 적용

상태 전환에는 페이지별 원자적 연산인 cmpxchg를 사용합니다. 두 스레드가 같은 페이지를 동시에 읽으면 한 스레드가 가져오기를 시작하고 다른 스레드는 대기 큐에서 기다림

서로 다른 페이지의 miss는 NAND 지연을 기다리는 동안에도 병렬로 진행할 수 있고, 또한 pin count를 사용해 PTE를 설치 중인 페이지가 동시에 제거되는 것을 방지

4. Evaluation

4.1 실험 설정

CXDVirt는 NVMeVirt의 PCI 장치 생성과 NAND 성능 모델을 확장해 구현

원격 NUMA 노드의 물리 메모리 96 GiB를 장치의 저장 공간으로 사용하고, 기본 DRAM 캐시 용량은 4.8 GiB로 설정

WSS 비율은 워크로드가 사용하는 데이터 크기를 DRAM 캐시 용량으로 나눈 값

0.35×에서는 워크로드가 캐시에 들어가지만, 2.2×에서는 데이터 크기가 캐시의 2.2배이므로 페이지 교체와 NAND 접근이 발생할 수 있음

4.2 Microbenchmark — 접근 지연과 병렬성

Pointer chasing은 현재 메모리에서 읽은 값으로 다음 접근 주소를 결정하는 벤치마크

이를 순차 및 무작위 접근으로 실행하여 DRAM hit와 miss의 지연시간 분포를 비교

두 에뮬레이터 모두 hit와 miss가 분리된 지연시간 분포를 보였으나 Cylon에서는 QEMU가 전역 lock을 잡은 채 NAND 대기를 처리하기 때문에, 한 vCPU가 연달아 요청을 처리하는 동안 다른 vCPU가 기다릴 수 있음

CXDVirt는 페이지별로 상태를 관리하므로 여러 페이지에서 동시에 발생한 miss를 병렬로 진행할 수 있음

장치 모델이 설정한 4 KiB 읽기 miss 지연은 6.2 µs

NAND 읽기 3 µs에 채널 전송 시간이 더해진 값

측정값과 설정값의 차이를 보면, 에뮬레이터 자체가 얼마만큼의 지연을 더하는지 비교할 수 있음

4.3 Macrobenchmark — 실제 워크로드

  • Splash-4 OCEAN은 쓰기 비중이 높은 8스레드 워크로드로, 전체 실행시간을 측정
  • Redis YCSB-C는 읽기 중심의 단일 스레드 워크로드로, 평균 및 P99 읽기 지연을 측정
  • 0.35× WSS에서는 NAND I/O가 발생하지 않으므로, 캐시에 들어가는 워크로드에서도 에뮬레이터가 얼마나 지연을 추가하는지 볼 수 있음. CXDVirt는 이 조건에서 원격 DRAM과 비슷한 결과를 보임

4.4 사례 연구 — Eviction과 Prefetch 정책

Redis 실험에서 FIFO와 CLOCK의 성능은 비슷했지만, LIFO는 최근에 가져온 페이지를 내보내므로 페이지를 다시 불러오는 비용이 커졌음

세 정책의 dirty eviction 횟수는 비슷했고, LIFO에서는 clean page의 퇴출이 특히 많았음

Redis 실험에서는 미리 가져온 페이지가 제때 사용되는 비율이 낮았고, 추가로 들어온 페이지가 캐시 공간을 차지하면서 eviction이 늘었음

다만 백그라운드 eviction이 느린 설정에서는 prefetch가 일부 느린 요청의 지연을 줄였음

요청을 처리하는 도중 캐시 공간이 필요할 때, 미리 가져온 clean page를 대신 내보내면 dirty page를 NAND에 쓰는 대기를 줄일 수 있었기 때문

  • (a) Eviction 정책 — FIFO와 CLOCK의 지연 분포는 비슷합니다. LIFO의 중앙 읽기 지연은 두 정책보다 1.8–1.9배 높고, clean eviction도 더 많음
  • (b) Prefetch 수와 읽기 지연 — 기본 조건에서는 N이 증가할수록 지연이 커짐. 백그라운드 eviction이 느린 조건에서는 N=8이 P80 지연을 42% 줄임
  • (c) Prefetch 활용도 — 미리 가져온 페이지 중 실제 요청이 오기 전에 준비되어 사용된 비율은 10% 미만
  • (d) 지연이 줄어든 이유 — 백그라운드 eviction이 느릴 때 N을 늘리면 page fault 처리 중 clean page를 내보내는 횟수가 늘고, dirty writeback으로 대기하는 시간이 줄어듦

5. Discussion & Conclusion

CXDVirt는 캐시 hit는 MMU의 직접 접근으로, 캐시 miss는 커널의 page fault로 처리 하여 CXL-SSD의 두 지연 경로를 재현

이 구조로 Cylon에서 관찰한 VM 처리 비용을 줄였으며, 같은 워크로드에서 캐시 교체와 prefetch 정책이 지연에 어떤 영향을 주는지도 관찰 가능

실험에서는 실제 CXL 연결의 지연을 원격 NUMA 메모리 접근으로 근사했는데, 논문은 실제 CXL 메모리를 저장 공간으로 사용하고, DRAM miss의 NAND 지연만 모델링하는 구성을 향후 과제로 제안
