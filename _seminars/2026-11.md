### 11월 12일

#### 논문발표 주희윤
*[HotStorage’24] Asymmetric RAID: Rethinking RAID for SSD Heterogeneity*

N drive RAID-5에서는 READ가 N배, WRITE가 N-1배 발생한다.

또한, 가장 성능이 낮은 HDD 또는 SSD의 성능을 따라간다.

cf) Fail-slow : 성능이 급격히 저하되는 현상 / Fail-stop : 동작이 완전히 멈추는 현상
=> **Asymmetric RAID**를 제안

Stripe가 RAID에 저장할 수 있는 용량을 결정함 (용량이 남아도 stripe로 구성할 수 없으면 사용X -> 공간낭비)

- 하나의 chunk는 하나의 SSD에 저장된다.
- 동일한 stripe에 속하는 chunk들은 각각 다른 SSD에 저장된다.

cf) SST : Stripe 상태를 관리하는 테이블

> 저자가 분석한 선행연구의 단점 외에, 제가 생각하는 단점은 무엇일까요?

#### 논문발표 김채원
*[ASPLOS'23] LeaFTL: A Learning-Based Flash Translation Layer for Solid-State Drives*

SSD는 Address Mapping Table을 저장하는 RAM이 필요하다.

- 선행연구
  Block-Level-FTL : Block 단위로 Table을 만들자
  DFTL : 일부만(Hot)만 Table에 넣자
  S-FTL : 압축하자

**Log Structured 방식을 사용한 mapping table 방식**

#### 연구 Seminar
OOB(Out of Bounds) : Page에 존재하는 metadata를 저장하는 위치(다른 여러가지 정보를 저장할 수도 있음)
OP(Over Provisioning) : 공간을 따로 빼두는 것 (제조사 or 사용자)
sector 단위 -> FTL -> page 단위

Write-hole : Parity가 data랑 맞지 않는 순간이 있기도 함
-> 이걸 줄이기 위해 이전 단계인 preread를 최소화하는게 필요

> CPU가 바쁘면 SSD가 일부 작업을 대신해주는 방식들이 있음

F2FS : NAND flash 기반 file system
segement 단위 -> section 단위 (-> zone 단위(HOT/COLD)
metadata(node), file data(block)

### 11월 26일

#### 논문발표 이동형
*[OSDI'26] Decentralized, Epoch-based F2FS Journaling with Fine-grained Crash Recovery*

F2FS : 기존의 하드디스크(HDD) 중심 파일 시스템(예: ext4)과 달리, 플래시 메모리의 물리적 특성(덮어쓰기 불가, 블록 단위 삭제 등)을 고려하여 설계된 file system
-> 입출력(I/O) 속도가 빠르고 저장장치의 수명을 연장해줌

- Crash가 발생하면 -> Checkpoint로 rollback을 하는데 이때, 성능 저하가 발생한다.

Journaling : write 도중에 error나면 데이터가 날라가기 때문에 따로 쓰고 이를 복사하는 방식
-> Journal file 크기가 커지는 문제도 있음

저자는 아래 3가지로 상태를 구분함 
1. Uptodate : page=disk인 상황
2. F2FSJ_Dirty : commit은 안된 상태 (*이거 필수)
3. Dirty : page 수정을 다 한 최신 상태

inode : 파일 시스템에서 파일이나 디렉터리의 모든 메타데이터(속성 정보)와 실제 데이터가 저장된 위치를 관리하는 자료구조
SSR 모드(Slack Space Recycling Mode) : F2FS 파일 시스템에서 저장 공간이 부족할 때, 별도의 정리 작업(가비지 컬렉션) 없이 기존 세그먼트 중간에 버려진 빈 블록(무효화된 공간)을 찾아 바로 새 데이터를 채워 넣는 공간 할당 방식
로지컬 로깅(Logical Logging) : 데이터나 파일 시스템에 변경이 생겼을 때, 바뀐 결과물(실제 데이터 블록 전체)을 통째로 기록하는 대신 '어떤 연산(명령)을 수행했는지' 그 **작업 내역만** 논리적으로 기록하는 방식

#### 연구 Seminar
- AFA(All-flash array) : 오직 SSD만으로 구성된 엔터프라이즈(기업용) 고성능 스토리지 장비 (HDD X)
-> 초고속 응답 속도(Low Latency)와 높은 입출력 처리량(IOPS)

- primary copy : 분산 스토리지나 DB 시스템에서 데이터를 여러 서버(노드)에 복제해 저장할 때, 데이터의 read write 요청을 대표로 처리하고 다른 복제본들의 최신 상태를 총괄·관리하는 '기준(원본) 데이터 복제본'
- write amplification : OS(Host)가 저장장치에 실제로 기록하려고 요청한 데이터 양보다, SSD 내부에서 물리적으로 훨씬 더 많은 양의 데이터를 쓰게 되는 현상
- context switch : O)가 하나의 CPU(코어)로 여러 프로그램(process or thread)을 동시에 실행하는 것처럼 보이게 하기 위해, 현재 실행 중인 작업의 상태(문맥)를 저장하고 다음 실행할 작업의 상태를 불러와 CPU 제어권을 넘겨주는 과정
- RU(Request unit) : 분산 스토리지 시스템에서 DB 작업(읽기, 쓰기, 쿼리 등)을 처리하는 데 필요한 CPU, 메모리, IOPS(디스크 입출력) 자원을 하나로 추상화하여 계산한 비용·성능 단위
- Dynamic I/O : 시간에 따라 random, sequential을 왔다 갔다 하는 방식
- MachineUnlearing : 삭제된 내용의 속성만 학습에서 삭제시키기 (다시 처음부터 학습할 필요가 X)

> SSD에 discard라는 명령어가 있음, 필요에 따라 dummy data를 쓰는 방식이 있는데 이걸 쓰면 write가 늘지만 이득이 더 큰 경우들도 있음
